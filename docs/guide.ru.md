## Требования

- Linux с cgroup v2 и делегированными пользователю контроллерами `memory`, `cpu`, `pids`;
- systemd ≥ 254 (пользовательский менеджер);
- Go 1.26 и [just](https://github.com/casey/just) для сборки.

## Установка

Перед установкой настройте пул по [инструкции первого запуска](../README.ru.md#первый-запуск). В частности, значение `pool_cpus = 16` по умолчанию не должно превышать число CPU машины.

```sh
just install
```

`just install` собирает `bin/aq` и:

- кладёт бинарник в `~/.local/bin/aq`;
- кладёт `aq.service` и `aq.slice` в `~/.config/systemd/user/`;
- копирует `deploy/config.example.toml` в `~/.config/agent-queue/config.toml`,
  только если конфига ещё нет (существующий не трогается);
- если в существующем конфиге `agent_processes` задан без `openclaude`, печатает
  подсказку: пока его нет в списке, сессии OpenClaude не считаются, а его команды
  принадлежат `cli`;
- выполняет `systemctl --user daemon-reload`, включает `aq.service` и
  (пере)запускает его — повторный `just install` обновляет работающий демон;
- копирует скилл `aq` каждому агенту свой: `deploy/skills/claude/aq` в
  `~/.claude/skills/aq` и, для OpenClaude, в `~/.openclaude/skills/aq`,
  `deploy/skills/codex/aq` в `~/.codex/skills/aq` (пути меняются через
  `CLAUDE_SKILLS`/`CODEX_SKILLS`/`OPENCLAUDE_SKILLS`, пустое значение — не
  ставить); хуки подключаются отдельно;
- если linger выключен, печатает подсказку: без `loginctl enable-linger $USER`
  демон и все задачи останавливаются при выходе из последней сессии.

Перед установкой проверьте `pool_memory` в примере конфига: значение по
умолчанию `16G` должно быть не больше `MemTotal` минус 10 % резерва, иначе демон
не запустится (`CONFIG_INVALID`).

Каталоги переопределяются переменными окружения: `BINDIR`, `UNITDIR`, `CONFDIR`,
`STATEDIR`, `CLAUDE_SKILLS`, `CODEX_SKILLS`, `OPENCLAUDE_SKILLS`, а `SYSTEMCTL`
(по умолчанию `systemctl --user`) — например, `SYSTEMCTL=true just install`
только раскладывает файлы.

Если установленный `aq` отвечает и в очереди есть задачи или резервы, `install`,
`uninstall` и `purge` сначала их показывают. Перезапуск для них безопасен: задачи
продолжают работать, `aq wait` переподключается, а посекундные замеры задач и
история защитника хоста сохраняются при штатной остановке и восстанавливаются
при старте.

Проверка после установки:

```sh
aq doctor
systemctl --user status aq.service
```

Все строки `aq doctor` должны быть `ok`. Если запустить `aq doctor` до первого
старта демона, он честно покажет `SLICE_MISSING`, `KILL_DROPIN_MISSING` и
`DAEMON_UNAVAILABLE`: `aq.slice` и runtime drop-in
`$XDG_RUNTIME_DIR/systemd/user/aq-.service.d/99-aq-kill.conf` создаёт сам демон
при старте. После `systemctl --user start aq.service` эти проверки проходят.

Удаление:

```sh
just uninstall   # останавливает и выключает сервис, удаляет бинарник и units
just purge       # то же плюс удаляет ~/.local/state/agent-queue (БД и логи)
```

`just uninstall` сохраняет БД, логи и конфиг. `just purge` удаляет состояние,
но конфиг тоже оставляет.

## Справка и вывод

`aq help` — список команд по группам, `aq help CMD` (или `aq CMD --help`) —
описание, флаги и примеры команды. Ошибка во флагах печатается один раз с
подсказкой, где смотреть справку.

Вывод зависит от того, кто его читает:

- **человек в терминале** — цветные состояния, таблицы, полосы памяти в `aq top`
  и `aq status`, короткие ID и длительности вида `3m05s`;
- **агент или скрипт** (stdout не терминал) — прежний простой текст, формат
  которого не меняется: его читают скиллы;
- `--json` — машинный вывод в любом режиме.

`AQ_UI=pretty` или `AQ_UI=plain` выбирает режим явно (например, для
`aq list | less -R`), `NO_COLOR=1` убирает цвета. Везде, где команда принимает ID
задачи или резерва, достаточно уникального префикса от 4 символов
(`aq status 5a0e71f2`), как его показывает `aq list`.

## Запуск задач

```sh
aq submit --memory 4G --cpus 2 --timeout 30m -- \
  bash -lc '/path/.venv/bin/python -m pytest -n "$AQ_CPUS"'
```

- `--memory` (без пригодной истории обязателен) — жёсткий лимит памяти задачи: `4G`, `512M`,
  `1024K`, `2T` (двоичные единицы), голое число — MiB; минимум `64M`.
- `--timeout` (обязательно) — максимальное время работы, например `30m`.
- `--cpus` — сколько CPU пула занять (по умолчанию 1); задаёт `CPUQuota`, это
  настоящий предел: 8 воркеров на 1 CPU делят его и работают до 8 раз
  медленнее. Если команда запускает больше воркеров (`pytest -n N`/`auto`,
  `make -jN`/`-j`), `submit` предупреждает в stderr (`hint: the command starts
  8 workers …`, `cpu_hint` в `--json`); дайте ей `-n "$AQ_CPUS"` или поднимите
  `--cpus`.
- `--priority low|normal|high`, `--name`, `--key` (идемпотентность: повторный
  `submit` с тем же ключом возвращает ту же задачу), `--session`, `--env K=V`,
  `--expected` (ожидаемое потребление, по умолчанию = `--memory`), `--json`.

Команда передаётся как argv, без неявного shell, и systemd не раскрывает в ней
переменные. Поэтому `$AQ_CPUS` нужно раскрывать внутри задачи: запуск через
`bash -lc '…'` в одинарных кавычках оставляет `$AQ_CPUS` нетронутым для вашего
shell, и раскрывает его уже `bash` внутри unit, где сервис выставил
`AQ_CPUS=<--cpus>`. Без `bash -lc` переменную раскрыл бы ваш shell до запуска
`aq` (и получил бы пустую строку). Кроме `AQ_CPUS` задача получает `AQ_JOB_ID`,
собственные `TMPDIR`/`TMP`/`TEMP`, а из вызывающего окружения — `PATH`, `HOME`,
`LANG`, `LC_*`, `VIRTUAL_ENV`. Задача с `--within` получает ещё
`AQ_RESERVATION_ID` и, если он есть у резерва, `AQ_DOCKER_PROJECT`: пометьте
контейнеры, которые задача запускает сама (testcontainers), меткой
`com.docker.compose.project=$AQ_DOCKER_PROJECT`, и aq посчитает их в стенде.

### Временные файлы живут в RAM и считаются памятью задачи

`TMPDIR` задачи — `/tmp/aq-<uid>-<slice>/<id>`, если `/tmp` — tmpfs (или внутри
`tmp_dir`, если он задан). Тогда временные файлы стоят оперативной памяти, а не
износа SSD: полный прогон pytest может создать и удалить сотню тысяч файлов в
`tmp_path`, а на диске каждый из них — запись плюс запись в журнал файловой
системы. Страницы засчитываются задаче, поэтому **`--memory` должен покрывать
то, что задача пишет в `$TMPDIR`**, а профили выучат это вместе с остальным
пиком. Каталог удаляется сразу после конца задачи (изнутри её юнита, так что и
остановленный демон его не оставит), включая каталоги, которые задача сделала
только для чтения.

Переполненный `/tmp` никогда не уводит временные каталоги на диск: если личный
корень не удалось создать при старте, он остаётся запланированным, барьер ниже
держит очередь, а следующий запуск его создаст. Отказ только для подложенного
корня в общем `/tmp` — симлинка или чужого каталога (тогда временные каталоги
идут в каталог состояния, а `aq doctor` предупреждает). Корень проверяется
заново при каждом запуске; задача под подложенным корнем падает с
`LAUNCH_FAILED`.

Переполненный tmpfs тоже ломает тесты, поэтому очередь ждёт, пока на файловой
системе временных каталогов меньше `min_tmp_free` (2G) свободного места или
меньше `min_tmp_inodes` (100000) свободных inode: `blocked_by=tmp`. Вложенные
задачи (`--within`) этот барьер обходят, как и дисковый. `aq top` показывает
файловую систему временных каталогов, а `aq doctor` предупреждает, когда они
откатились в каталог состояния (`/tmp` не tmpfs и `tmp_dir` не задан) или места
мало.

```toml
# tmp_dir = "/tmp"      # не задан: /tmp, если это tmpfs, иначе каталог состояния
min_tmp_free = "2G"
min_tmp_inodes = 100000
```

`aq submit` печатает id задачи и сразу возвращает управление.

## Профили и оценки

Давайте повторяющимся прогонам стабильное `--name`, например `tests-unit`.
Без явного `--profile` профиль — `<основной корень репозитория>:<name>`;
он общий для всех worktree. `--project` заменяет корень, а `--profile P`
задаёт имя целиком. Без имени и профиля история не собирается.

Называйте нагрузку, а не прогон: один и тот же набор тестов сохраняет имя от
релиза к релизу. Версия, дата, коммит или номер задачи в имени (`tests-b15`)
при каждой смене начинают новую, пустую историю; этот контекст держите вне aq.
Другое имя уместно, когда другая форма памяти (другой набор, другое число
воркеров, элемент матрицы вроде `tests-pg16`). Внутри worktree не задавайте
`--project`, иначе у этого worktree будет своя история.

Если у имени ещё нет истории, а у других имён того же репозитория есть,
`aq submit` предупреждает в stderr (`known_names` в `--json` и MCP):

```
hint: no history for name "tests-wave2" here; names with history: tests, e2e (reuse one for the same workload)
```

Первый запуск требует `--memory`. После хотя бы одного пригодного прогона
память можно опустить:

```sh
aq submit --name tests-unit --memory 2G --cpus 2 --timeout 15m -- pytest tests/unit
aq profile list
aq profile show tests-unit          # короткое имя = <корень репозитория>:tests-unit
aq submit --name tests-unit --cpus 2 --timeout 15m -- pytest tests/unit
```

Пригодны успешные прогоны и `COMMAND_FAILED` с ненулевыми пиком и длительностью.
OOM, таймауты и отмены не повышают лимит автоматически. По последним 10 пригодным
прогонам лимит равен максимальному пику × 1.2 с округлением вверх до MiB
(от 64 MiB до размера пула); expected — p90 выборок `memory.current`, не выше
лимита. Явный `--memory` всегда выигрывает, `--expected` можно переопределить.
Оценка длительности — p90 истории, ограниченный `--timeout`.

Перед тяжёлым прогоном узнайте, придётся ли ждать:

```sh
aq estimate --name tests-unit --cpus 2 --timeout 15m
# queued: position 2, expected start in 12m0s
# memory: 1.2 GiB limit, 900 MiB expected
# duration: 3m0s (profile)
# blocked by: pool_memory ...
# confidence: partial
```

`aq estimate` ничего не ставит в очередь. Без истории можно передать `--memory`,
а без оценки длительности — `--timeout`. Уверенность: `now`, `history`,
`partial`, `timeout` или `unknown`. `aq list` показывает колонку `START`,
`aq status` — ожидаемый старт ждущего элемента.

Backfill разрешает более поздней задаче обогнать заблокированную голову,
если она помещается сейчас и по оценке освободит ресурсы до старта головы
или укладывается в свободный остаток после головы. Резервы обгоняют только
через этот остаток: общие слоты снятия могут задержать освобождение.
Давление, диск, место для временных файлов и восстановление закрывают обгон; недостижимая голова тоже.
Оценки могут ошибаться, поэтому фактический старт иногда позже прогноза.
Отключение — `[scheduler] backfill = false`.

## Наблюдение и ожидание

```sh
aq list              # активные задачи: состояние, память, ожидание, BLOCKED_BY
aq list --all        # включая завершённые
aq status <id>       # подробности: состояние, причина, пик памяти, код выхода
aq result <id>       # то же плюс пути к stdout.log/stderr.log
aq logs <id> [--stream stderr] [--tail 100] [--follow]
aq wait <id>         # ждёт завершения, печатает итог и выходит с кодом:
```

| Код `aq wait` | Значение |
|---|---|
| 0 | `SUCCEEDED` |
| 1 | `COMMAND_FAILED` (команда вышла с ненулевым кодом; он в `aq status`) |
| 2 | `OOM`, `OOM_GROUP`, `OOM_HOST_GUARD` |
| 3 | `TIMEOUT` |
| 4 | `CANCELLED` |
| 5 | инфраструктура: `LAUNCH_FAILED`, `LOST`, `STORAGE_FULL`, `REJECTED` |
| 6 | резерв больше не удерживается (см. «Резервы») |
| 64 | ошибка использования |
| 69 | демон недоступен |

Для упавшей задачи `aq wait` ещё печатает в stderr последние 5 строк её stderr
(`stderr (last 5 lines):`), а `aq result` заканчивается ими (`stderr tail:`); в
`--json` это `stderr_tail`. Большинство падений читается оттуда без `aq logs`.

Каждый элемент в очереди говорит, почему ждёт: `aq list`, `aq status`
(`blocked by:`) и `--json` (`blocked_by`, `blocked_detail`). Причина — его
собственный блокер с цифрами (например, `live_memory: … need 8.1 GiB (floor
3.1 GiB + requested 5.0 GiB)`), блокер головы, когда давление, диск, место для
временных файлов или восстановление держат всю очередь, или `queue`: он бы
поместился сейчас, но его запуск задержал бы элемент в голове. `aq submit` и
`aq reserve` отвечают после ближайшего прохода допуска и уже знают, стартовал
ли элемент; если нет, печатают в stderr `queued: position N, blocked by …`
(строка в stdout не меняется), и `aq wait` делает так же, когда начинает ждать
элемент из очереди.

Типичный сценарий агента:

```sh
id=$(aq submit --memory 4G --cpus 2 --timeout 30m -- make test)
aq wait "$id"; code=$?
aq logs "$id" --tail 50
```

У всех команд просмотра есть `--json` для разбора программами.

Если пик памяти завершённой задачи разошёлся с заявленной ожидаемой памятью,
строка `aq wait` заканчивается подсказкой для следующей оценки; она же приходит
в уведомлении `task_finished` и в поле `memory_fit` в `--json`:

```
… SUCCEEDED exit=0 waited=0s ran=4m12s memory: peak 0.8 GiB is 19% of expected 4.0 GiB (overestimated: lower --expected to 983 MiB, keep --memory as the limit)
```

Подсказка появляется, когда пик выше 110% или ниже 50% ожидаемой памяти и
отличается от неё хотя бы на 256 MiB. О переоценке сообщается только для
прогона, дошедшего до конца (`SUCCEEDED` или `COMMAND_FAILED`): таймаут или
отмена обрывают пик. Переоценку исправляют через `--expected`: именно его
списывает пул, а `--memory` остаётся лимитом-убийцей, и пик одного прогона —
не безопасный лимит для следующего. Память, взятая из профиля, подсказки не
получает: свою оценку aq поправляет по истории сам.

`aq top` (или `--json`) показывает один снимок: память/PSI/swap,
непересекающиеся физические категории agents / run by agents / docker / tasks /
other, отдельно обязательства задач/стендов/бюджетов и причины задержки головы.
Эти две картины между собой не складываются. Если «всё медленно», начните с
этого снимка. «Agents» — сами процессы агентов (`[stats] agent_processes`);
«run by agents» — то, что они запустили мимо aq и docker, например набор тестов
или сборку напрямую (`spawned` в `--json`, по каждому агенту); «other» — всё
остальное: система, терминальный мультиплексор, ядро. `aq stats` хранит то же
деление во времени в разделе «Host memory» (область `memory`).

`aq top` также показывает число сессий агентов, общий объём памяти агентов и
их дочерних процессов и до трёх сессий, простаивающих не меньше
`[sessions] idle_after` (по умолчанию 12 часов). `aq top --sessions`
показывает имя (или PID), клиент, каталог проекта, память агента и дочерних
процессов, своп и время простоя каждой сессии. Прочерк означает, что время
простоя неизвестно. Если замер процессов завершился ошибкой, текстовый режим
выводит её и завершается с кодом 69. В JSON ошибка находится в `physical.error`.

### Временные файлы и тревоги по сессиям

Сводка инвентаризации в `aq top` показывает суммарный размер осиротевших
элементов и кандидатов, а также до трёх крупнейших элементов. Если временные
каталоги задач и корень сканирования находятся на одной файловой системе,
сводка входит в строку `tmp:`. Иначе она выводится в строке `tmp scan:` с
данными о заполнении файловой системы сканирования. `aq tmp` показывает
заполнение файловой системы, оба итога, давность сканирования, число частично
просканированных элементов и 30 крупнейших элементов. Число и объём элементов
в каждом состоянии считаются по всей инвентаризации. Звёздочкой `*` отмечены
частично просканированные элементы. `aq tmp --all` показывает все элементы,
а `aq tmp --json` выводит полный отчёт. Поле `fs` содержит общий и свободный
объём в байтах, число inode и признак tmpfs для корня сканирования. Если
данные недоступны, поле равно `null`.
По умолчанию демон сканирует раз в 10 минут. `aq tmp --rescan` ждёт уже
запущенный проход. Если прохода нет, команда возвращает отчёт моложе минуты
или запускает сканирование, если отчёту минута или больше либо его ещё нет.
В этом выпуске команда только собирает сведения и не удаляет файлы.

| Состояние | Значение |
|---|---|
| `aq_task` | Элемент принадлежит задаче aq. |
| `in_use` | Элемент используется процессом или просканирован частично. |
| `live` | Недавний scratchpad активного проекта Claude. |
| `candidate` | Старый scratchpad активного проекта Claude, который сейчас не используется процессами. |
| `orphan` | Старый элемент без использующих его процессов и без известного активного владельца. |
| `recent` | Остальные элементы со временем mtime или ctime в пределах `[tmp] orphan_after` (по умолчанию 24 часа), включая записи внутри каталогов. |

| Срабатывание | Снятие | Порог по умолчанию |
|---|---|---|
| `tmp_full` | `tmp_full_normal` | Занято 70% места или inode в /tmp. |
| `swap_full` | `swap_full_normal` | Занято 75% свопа. |
| `sessions_heavy` | `sessions_heavy_normal` | Агенты и их дочерние процессы используют в сумме 6 GiB памяти. |
| `sessions_idle` | `sessions_idle_normal` | Три сессии простаивают не меньше `[sessions] idle_after`. |
| `tmp_orphans` | `tmp_orphans_normal` | Осиротевшие элементы и кандидаты вместе занимают 2 GiB. |

Первые четыре тревоги срабатывают, когда среднее за `[alerts] window`
(по умолчанию 10 минут) достигает порога, и снимаются, когда оно падает ниже
половины порога. В окне должно набраться не меньше половины замеров,
ожидаемых при интервале `[stats] sample_interval`. Для срабатывания или снятия
`tmp_orphans` нужны два полных сканирования по расписанию подряд.
В строке `alerts:` команда `aq top` показывает названия, время срабатывания
и значения активных тревог. В `aq top --json` они содержатся в поле `alerts`.
Если сканирование элемента превысило лимит времени, в заголовке отчёта
появляется сообщение `incomplete pass: tmp_orphans paused`. Тревога сохраняет
значение последнего полного прохода. Нечитаемые элементы учитываются как
частично просканированные, и проход остаётся полным. Если нельзя прочитать
список записей в `claude-<uid>` или получить доступ к этим записям, каталог
показывается как один частичный элемент `in_use`, а остальные элементы
сканируются дальше. Нулевой порог отключает соответствующую тревогу.
Вебхук оператора получает одно уведомление о срабатывании и одно о снятии.

### Снимок для панели

Для панелей и статус-баров `aq dashboard` печатает один JSON-документ
(`version` 1): память хоста, флаги pressure и guard, обязательства пула, счётчики
очереди, все незавершённые элементы в порядке очереди (у ждущих `position`,
`blocked_by` и `expected_start`; у запущенных и удерживаемых `memory_current` —
сколько они используют сейчас), элементы, завершившиеся за последние 24 часа
(`recent`, не больше 20), и итоги задач за эти сутки (`day`: finished,
succeeded, failed, cancelled, OOM, timeout, медиана и максимум ожидания). Поля
элементов те же, что в `aq list --json`. Тот же документ демон держит в
`$XDG_RUNTIME_DIR/agent-queue/dashboard.json` (tmpfs, на диск ничего не пишется).
Файл переписывается сразу, когда элемент меняет состояние или место в очереди
либо когда тревога срабатывает или снимается,
не чаще раза в 10 секунд, когда меняются только цифры, и не реже раза в 30
секунд. При чистой остановке демон удаляет файл. Панель может следить за файлом
вместо опроса: файла нет — демон не запущен; `at` старше минуты — демон упал.

- `sessions` появляется после первого успешного замера. В нём суммы
  `agent_bytes` и `run_bytes` и список сессий в `items`, со свопом и временем
  простоя, если оно известно.
- `tmp` появляется после первой успешной инвентаризации. В нём заполнение
  файловой системы (`fs`), `scanned_at`, `orphan_bytes`, `candidate_bytes` и
  до 50 крупнейших элементов в `items`. Поле `complete` показывает, уложилось
  ли сканирование каждого элемента в лимит времени. `partial_items` учитывает
  частично просканированные элементы во всей инвентаризации.
- `alerts` содержит активные эпизоды с полями `name`, `since`, `value` и
  `threshold`. Когда активных эпизодов нет, это пустой массив.

С полями хоста нужна осторожность. `guard_active` говорит лишь, что host guard
держит потолок слайса ниже пула; если пул близок к памяти хоста, так бывает
всегда, когда другие программы занимают хоть сколько-то памяти, и это не
предупреждение. `guard_ceiling` — потолок, который guard записал последним (0 до
первой записи), а `guard_cutting` равен true, когда этот потолок ниже того, что
aq пообещал работе в своём слайсе: ожидаемой памяти запущенных задач плюс
бюджетам задач у резерваций. Тогда задачу могут убить раньше, чем она дойдёт до
памяти, с которой её допустили; предупреждать в панели стоит именно по этому
флагу.

```sh
aq stats                      # сводка на один экран и «Worth a look»
aq stats disk                 # одна область подробно
aq stats --all --since 7d     # все разделы целиком
aq stats --since 30d --profile /path/to/repo:tests-unit --json
aq stats export --since 7d --format jsonl
aq stats export --since 7d --format csv --table host
```

`aq stats` без аргументов печатает сводку на один экран: очередь, исходы,
память, диск и агенты за период, а ниже короткий список «Worth a look». Каждый
пункт называет область, которую стоит открыть. `aq stats ОБЛАСТЬ` печатает
таблицы этой области, обрезанные до первых строк (`N more: aq stats ОБЛАСТЬ
--all`); области: `tasks`, `profiles`, `disk`, `memory`, `reservations`,
`notify` и `incidents`. `aq stats --all` печатает все разделы целиком. `--json`
всегда отдаёт полную сводку, какая бы область ни была указана. Сводки
охватывают исходы и ожидание задач, точность профилей, очередь и хост, запись
на диск, резервы, доставку, срабатывания хука и инциденты OOM/PSI. Фильтр
профиля возвращает только элементы и прогоны этого профиля. Таблицы выгрузки:
`items`, `runs`, `host`, `incidents`, `events`, `disk`, `hook`; CSV требует
`--table` (в `disk` лежит почасовая запись по источникам, см. «Запись на
диск»).
Команды, окружение, cwd, идентификаторы сессий и тексты ошибок доставки
в статистику и выгрузку не входят.

Пример куска сводки:

```
Disk       3.0 TiB written (20.0 GiB/h) · aq tasks 2%
           top: session:session-3.scope 1.0 TiB (≈ claude ~/src/shop)
...
Worth a look
  ! disk          session:session-3.scope wrote 1.0 TiB, ≈ all of it claude ~/src/shop
  ! reservations  e2e-stand held 7 GiB·h it never used
```

«Reservation fit» сравнивает записанные пики резервов каждого имени с
заявленным: стенд с `--memory` (только с `--docker-project`, иначе он не
замеряется) и самый нагруженный момент вложенных задач с `--task-memory`, как
p50/p90 отношения пика к заявке. `UNUSED GiB·h` складывает заявленную память
сверх пика, умноженную на время удержания: память, которую очередь не могла
отдать, хотя её никто не использовал. Сверху имена, у которых её больше всего.
Пики записываются, когда резерв освобождают или начинается его снятие;
перезапуск демона во время удержания теряет пики, замеренные до него.

OOM-убийства ядра вне aq разбиты по cgroup, где они случились: слайс
пользовательского менеджера (`app.slice`, собственный слайс тестового набора),
сессия входа, где агенты запускают свои команды (`session-3.scope`), или
`system.slice` (сервисы и контейнеры docker), например `kernel OOM kills outside
aq: 134 (aqtest.slice 120, ended cgroups 9, app.slice 2)`. `ended cgroups` —
cgroup пользователя, удалённые раньше, чем aq успел их назвать, например слайс
тестового набора, который появился и исчез между двумя замерами (раз в 10 с).
Неназванные убийства случились в другом месте, вне слайса пользователя и
`system.slice`.

### Запись на диск

Завершённая задача записывает, сколько байт она записала на физические диски и
прочитала с них (`disk:` в `aq result`, `io_write_bytes`/`io_read_bytes` в
`--json`). `aq stats` показывает профили, которые записали больше всего: всего,
медиана и максимум за прогон, а `aq profile show` — медиану записи за прогон.
Набор тестов, который пишет гигабайты за прогон, изнашивает SSD и тормозит
ввод-вывод всем: обычно это база без `fsync=off`, установка зависимостей без
кэша или сборка каждый раз в новый каталог.

Числа берутся из `io.stat` задачи (device-mapper, md, loop и zram пропускаются,
чтобы ничего не посчитать дважды; запись, которая к концу задачи ещё в page
cache, не учитывается). Для этого user manager должен получить контроллер `io`,
а systemd по умолчанию его не делегирует; без него поля отсутствуют (неизвестно,
а не ноль), а `aq doctor` показывает предупреждение `IO_NOT_DELEGATED`. Включить:

```sh
sudo mkdir -p /etc/systemd/system/user@.service.d
printf '[Service]\nDelegate=cpu cpuset io memory pids\n' | sudo tee /etc/systemd/system/user@.service.d/delegate-io.conf
sudo systemctl daemon-reload
# затем перезагрузка (или systemctl --user daemon-reexec) и рестарт aq.service
```

#### Запись всего хоста по источникам

Счётчики задач не видят большую часть того, что пишет машина. Каждый замер (30 с)
демон ещё читает счётчик физических дисков хоста и делит байты по тем, кто их
записал, на двух уровнях. Источники в сумме дают число хоста:

- `aq`: задачи и резервы, запущенные через aq;
- `docker:ПРОЕКТ`: контейнеры, сгруппированные по compose-проекту (по метке,
  которую `--docker-project` привязывает к резерву стенда);
- `system:UNIT` и `user:UNIT`: службы вроде journald и приложения; со
  стороны системы источник — каждый ребёнок `system.slice`, так что вложенный
  слайс вроде `system-getty.slice` (вместе с короткоживущими unit'ами внутри)
  или точка монтирования — отдельный источник;
- `session:ИМЯ`: сессия входа, а значит и команды, которые агенты запускают
  мимо aq;
- `other`: остальное, считается за период как число хоста минус названные
  источники, поэтому ничего не считается дважды. Это то, что не измерил ни
  один источник: ядро и журнал файловой системы, другие пользователи, cgroup без
  делегации `io`. Он такой же писатель, как остальные: в строке Disk сводки он
  виден как `unattributed N%` начиная с 10%, с четверти байт хоста и 10 GiB
  становится пунктом «Worth a look», а тревога называет его среди главных
  источников.

Второй уровень называет агентов. Внутри источника `aq stats disk` может
написать рядом `≈ claude ~/proj`: дерево процессов агента
(`[stats] agent_processes` и его потомки в той же cgroup) и каталог его проекта. Потомок, однажды замеченный
в дереве агента, считается за него, пока жив, в том числе после выхода агента.
Это оценка, и в сумму она не
входит. Она считает запись в момент, когда страница стала грязной, а источник —
когда байты ушли на устройство, поэтому за секунды они расходятся, за часы
сходятся. Ограничения: запись потомков, которых агент передал init после
последнего замера, есть в источнике, но не в оценке агента; отменённая запись
удалённого файла приписывается процессу, удалившему файл, а не писавшему;
запись, пока демон не работал, теряется.

`aq stats disk` показывает сумму и скорость за период, источники, самые тяжёлые
часы (у каждого главный писатель, им может быть и `other`) и задачи, чьи прогоны записали больше всего; `aq stats export --table disk`
отдаёт почасовые строки. В `aq top` есть строка `disk:` с текущей скоростью и
главным писателем; если последний замер старше 3 минут, она помечается как
устаревшая.

Для записи нужна та же делегация `io`, что и выше. Почасовые строки хранятся
столько же, сколько история задач (`history_max_age`, но не меньше `logs_max_age`).

#### Тревога о записи на диск

Окно делится на пять равных частей, а байты каждого замера распределяются по
частям, которые накрывает его интервал; в окно идёт только доля, попавшая в
него, — и для частей, и для средней скорости, объёма и главных источников. Если хотя бы в четырёх частях скорость не
ниже `alert_rate` (одиночный короткий всплеск не считается), aq один раз
отправляет через webhook уведомление `disk_writes_high`: скорость, сколько это
длилось, объём и главные источники (с оценкой по агентам):

```
disk writes at 120 GiB/h for 10m (20 GiB): session:session-3.scope 118 GiB/h (≈ claude ~/proj)
```

За эпизод оно приходит один раз. Когда средняя скорость за целое окно падает ниже
половины порога, следует `disk_writes_normal` с объёмом эпизода и главным писателем.
Через вебхук оператора также идут пять событий срабатывания и пять событий снятия
из раздела [Временные файлы и тревоги по сессиям](#временные-файлы-и-тревоги-по-сессиям).
aq только сообщает: он ничего не останавливает и не ограничивает. Настройка в
`config.toml`:

```toml
[disk]
alert_rate = "50G"     # байт в час; "0" выключает тревогу
alert_window = "10m"   # не меньше 5 x stats.sample_interval
```

Без `alert_window` окно — 10 минут или пять интервалов замера, если
`stats.sample_interval` длиннее 2 минут. Когда тревога выключена, окно не
проверяется.

## Хранение

Раз в 10 минут и после восстановления демон удаляет логи завершённых элементов
старше 7 дней, включая логи снятий резерва. Общий предел `jobs/` — 5 GiB:
при превышении удаляются старейшие завершённые. Активные элементы, в том числе
`TEARDOWN_FAILED/UNKNOWN`, сохраняются. После удаления `logs_pruned = true`,
`aq logs` отвечает `removed by retention`, а `aq result` не показывает пути.
Сироты без строки БД и неактивные временные каталоги удаляются после часа.

История элементов, их события/прогоны, инциденты и повёрнутые файлы хука
хранятся 90 дней. Хост измеряется раз в 30 секунд, хранится 30 дней;
старше 2 дней остаётся первая строка каждой 10-минутной корзины со span 600 с.

Новые ключи (полный пример — `deploy/config.example.toml`):

```toml
[profiles]
window = 10
memory_percentile = 90
duration_percentile = 90
limit_margin = 1.2
[scheduler]
backfill = true
[retention]
logs_max_age = "7d"
logs_max_total = "5G"
history_max_age = "90d"
samples_max_age = "30d"
samples_full_res = "2d"
[stats]
sample_interval = "30s"
agent_processes = ["claude", "openclaude", "codex"]
```

Длительности конфига поддерживают дни: `7d`, `1d12h`. История берёт 1–100
прогонов, процентили — 50–100, запас лимита — 1–4. Хранение положительно,
`samples_full_res < samples_max_age`, общий предел логов не меньше 256 MiB,
интервал хоста — от 5 с до 5 мин; имена процессов непусты и без `/`. Это имена
процессов, которые aq считает агентами при замере памяти, в `aq top --sessions`
и при поиске агента-предка команды (`openclaude` — OpenClaude). OpenClaude даёт
процессу это имя через заголовок терминала; с заданной
`CLAUDE_CODE_DISABLE_TERMINAL_TITLE` процесс остаётся `node`, и aq не считает
его агентом. `openclaude` есть в списке по умолчанию; конфиг, написанный ранней
версией, сохраняет свой список — добавьте `openclaude` туда: пока его нет,
установщик печатает подсказку.

## Диагностика: `aq doctor`

`aq doctor` проверяет cgroup v2, делегирование контроллеров, наличие слайса,
реальное применение `MemoryMax` (пробный unit на 64M), конфиг, свободное место,
доступность демона, версию systemd и runtime drop-in остановки задач. Каждая
ошибка помечена кодом (`CGROUP_V2_MISSING`, `CONTROLLER_MISSING`,
`SLICE_MISSING`, `PROBE_FAILED`, `CONFIG_INVALID`, `DISK_LOW`,
`DAEMON_UNAVAILABLE`, `SYSTEMD_TOO_OLD`, `KILL_DROPIN_MISSING`) и подсказкой.
`IO_NOT_DELEGATED` — предупреждение, а не сбой: задачи работают, но не
записывают байты диска (см. «Запись на диск»). `TMP_ON_DISK` (временные каталоги
откатились в каталог состояния) и `TMP_LOW` (очередь ждёт места для временных
файлов) — тоже предупреждения.

## Изменение пула

Отредактируйте `~/.config/agent-queue/config.toml` (`pool_memory`, `pool_cpus`,
`reserve_floor_percent` и т. д.; все ключи с описанием — в
`deploy/config.example.toml`) и перезапустите демон:

```sh
systemctl --user restart aq.service
```

Работающие задачи при перезапуске демона не прерываются: это отдельные units
systemd, и новый демон подхватывает их состояние и результаты. Ожидающий
`aq wait` переподключается до 10 минут (пишет в stderr
`aq: lost the daemon (restart?); reconnecting`) и затем сообщает результат как
обычно. При штатной остановке демон сохраняет замеры памяти работающих задач и
историю защитника хоста и восстанавливает их при старте; после падения они
теряются. Каждый перезапуск — операторское событие `daemon_restarted` (версия,
штатная ли остановка, что подхвачено), оно уходит в webhook, если он настроен.

## OOM и другие сбои

Если задача превысила `--memory`, ядро убивает её внутри её cgroup, а `aq wait`
выходит с кодом 2. Подробности:

```sh
aq status <id>                    # причина OOM, пик памяти (memory peak)
journalctl --user -u aq-<id>      # журнал unit задачи (systemd: oom-kill и т. п.)
aq logs <id> --stream stderr
```

`OOM_GROUP` — задачу убил лимит пула (`aq.slice`): увеличьте `--memory` или
уменьшите параллелизм команды. `OOM_HOST_GUARD` — защитник хоста, временно
снизивший потолок слайса из-за нехватки памяти на машине, обычно из-за чего-то
вне aq: больший `--memory` не поможет, запустите снова, когда память
освободится. Каждый раз, когда из-за потолка защитника ядро убивает в слайсе,
aq записывает, кто тогда держал память (не чаще раза в 5 минут; потолок ниже
пула, который никого не убил, не записывается): самые большие cgroup и
процессы (с агентом, который запустил каждый, если есть) и память вне всех
cgroup (ядро, драйверы, zram). `aq stats` показывает
число и последние три снимка в разделе Incidents («host guard cut the aq slice
N times»), `aq stats export --table incidents` — все, как `guard_engaged`.

## Отмена

```sh
aq cancel <id> [--reason "..."]
```

Задача в очереди снимается сразу. У работающей останавливается весь unit:
systemd шлёт SIGTERM, через `cancel_grace` (по умолчанию 10 с) — SIGKILL всем
процессам cgroup, включая ушедших в `setsid`/демонизированных потомков.

## Резервы

Резерв нужен, когда память занимает не сама команда, а то, что живёт дольше неё
или вне её cgroup: compose-стенд (база, брокер, сервисы приложения) или
контейнеры, которые тесты поднимают через testcontainers. Контейнеры работают в
cgroup dockerd, лимиты задачи на них не действуют, и без резерва пул о них не
знает. Резерв заранее занимает в пуле память (и, если нужно, CPU) стенда на
заданный срок, а также бюджет для задач, которые будут работать со стендом.

```sh
cat > teardown.sh <<'EOF'
docker compose -p myapp-e2e down -v --remove-orphans
EOF

out=$(aq reserve --memory 6G --cpus 2 --task-memory 4G --task-cpus 4 \
  --ttl 2h --teardown teardown.sh --docker-project myapp-e2e)
# out: "<id> GRANTED" или "<id> QUEUED position=… blocked_by=…"
id=${out%% *}
aq wait "$id"                      # ждёт выдачи; код 0 = GRANTED/EXPIRING
docker compose -p myapp-e2e up -d  # стенд поднимаем только после выдачи
```

- `--memory` (обязательно) — память стенда; `--cpus` — CPU стенда (по
  умолчанию 0).
- `--task-memory` и `--task-cpus` — бюджет вложенных задач (`submit --within`),
  задаются только вместе: минимум `64M` и 1 CPU.
- `--ttl` (обязательно) — срок резерва, отсчитывается от выдачи; не больше
  `max_ttl` (24 ч).
- `--teardown` (обязательно) — файл скрипта снятия (до 64 KiB).
- `--docker-project` — compose-проект стенда. Демон раз в 5 с замеряет через
  `/var/run/docker.sock` память контейнеров с меткой
  `com.docker.compose.project=<project>` и считает ещё не выбранной только
  разницу между заявленным и замеренным. Без `--docker-project` весь `--memory`
  стенда всё время жизни резерва считается невыбранным: это надёжно, но память
  недоиспользуется. Один проект может принадлежать только одному незавершённому
  резерву (пока тот не `TORN_DOWN`, `RELEASED` или `CANCELLED`). Если стенд
  превысил заявленное, записывается уведомление с замеренным объёмом в процентах
  от заявленного и тремя самыми большими контейнерами (по compose-сервису или
  имени). Контейнер считается как `memory.current` минус неактивный файловый
  кеш.
- `--name`, `--key`, `--session`, `--priority`, `--env K=V`, `--json` — как у
  `submit`. `--name` ещё и задаёт ключ истории резерва (`<корень
  репозитория>:<name>`, общий для worktree), см. ниже.

Стенд и бюджет задач вместе занимают пул, пока резерв не освобождён. Со
стабильным `--name` резерв списывает с пула столько, сколько использовали
прошлые резервы с этим именем, как задача по своему профилю: наибольший
замеренный пик стенда (только с `--docker-project`) и наибольшую одновременную
память вложенных задач, каждое по последним `[profiles] window` (10) резервам,
где это записано, × `limit_margin` (1.2), но не больше заявленного. `--memory` и
`--task-memory` остаются потолками: вложенные задачи допускаются в пределах
заявленного бюджета, а `stand_over_declared` сравнивает с `--memory`.
`aq status` показывает `(charged … by history)` в строках `stand:` и `budget:`,
в `--json` есть `memory_expected` и `task_memory_expected`. Резерв
встаёт в очередь так же, как задача, а `aq reserve` отвечает после ближайшего
прохода допуска: сразу `GRANTED`, если влез, иначе `QUEUED` с позицией и
причиной ожидания.

### Скрипт снятия

При `reserve` клиент передаёт содержимое скрипта, и демон хранит его копию в
`jobs/<id>/teardown.sh`. По истечении срока демон запускает `bash <копия>`
отдельным unit `aq-teardown-<id>.service` в слайсе `aqtd.slice`: вне пула, с
лимитами `teardown_memory`, 1 CPU и `teardown_timeout` (по умолчанию 5 мин).
Скрипт должен быть:

- **самодостаточным** — не зависеть от файлов рабочего каталога: к моменту
  снятия worktree может быть удалён. cwd скрипта — исходный каталог резерва,
  если он ещё существует, иначе пустой служебный `jobs/<id>/teardown-<n>/cwd`;
  исходный путь передаётся в `AQ_ORIGINAL_CWD`, id резерва — в
  `AQ_RESERVATION_ID`;
- **идемпотентным** — повторный запуск безопасен: `docker compose -p <project>
  down`, а не «удалить то, что я создал».

Окружение скрипта захватывается при `reserve`: то же, что у `submit`, плюс
`DOCKER_HOST`, `DOCKER_CONTEXT`, `DOCKER_CONFIG` и `--env`.

### Задачи на стенде: `submit --within`

pytest против стенда, как и тесты, которые сами поднимают контейнеры через
testcontainers, запускаются внутри резерва:

```sh
aq submit --within "$id" --memory 3G --cpus 4 --timeout 30m -- \
  bash -lc 'pytest -n "$AQ_CPUS" tests/e2e'
```

Вложенная задача не проходит повторный допуск в пул и не стоит в очереди: она
стартует сразу, в бюджете резерва. Если сумма `expected` неоконченных вложенных
задач вместе с новой больше `--task-memory` или сумма их CPU больше
`--task-cpus`, `submit` сразу отказывает (`REJECTED`, «task budget», код 5).
Так два агента, получившие по резерву, не блокируют друг друга. Контейнеры,
которые поднимает сама задача, живут в cgroup dockerd, а не задачи: заложите их
память в `--memory` резерва (замер `--docker-project` видит только контейнеры
compose-проекта), и пусть скрипт снятия убирает и их.

### Продление и освобождение

```sh
aq extend "$id" --ttl 1h   # срок истечёт не раньше чем через 1 ч от сейчас
aq release "$id"           # стенд погашен самим агентом: освободить без скрипта
```

`extend` не прибавляет срок, а задаёт «не раньше чем сейчас + D», поэтому
повтор безопасен; продлить можно в `GRANTED` и `EXPIRING`. `release`
освобождает выданный резерв, если в нём нет неоконченных вложенных задач, а
резерв из очереди отменяет (`CANCELLED`). `aq cancel` для резерва действует
только в очереди. `release` ещё и печатает, как пики соотносятся с заявленным,
по тем же порогам, что и у задач: замеренный пик стенда с `--memory` (с
`--docker-project`) и наибольшая одновременная память вложенных задач с
`--task-memory`, с объёмом, который стоит заявить в следующий раз (пик × 1.2):
`… RELEASED stand peak 1.1 GiB is 32% of declared 3.4 GiB (overestimated: next
time --memory 1.3 GiB); task budget peak 1.0 GiB is 25% of declared 4.0 GiB
(overestimated: next time --task-memory 1.2 GiB)`. Это остаётся в диагностике `aq result`, а `aq status`
показывает оба пика в строках `stand:` и `budget:`.

### Контейнеры вне compose-проекта

aq замеряет стенд по метке `com.docker.compose.project`, которую ставит compose,
а другие инструменты нет:

- **testcontainers** и другой тестовый код, который сам запускает контейнеры:
  запускайте его через `aq submit --within RES_ID` резерва с `--docker-project`
  и давайте каждому контейнеру метку
  `com.docker.compose.project=$AQ_DOCKER_PROJECT` (labels запроса контейнера).
  Если пометить контейнеры нельзя, заложите их память в `--memory` резерва и не
  указывайте `--docker-project`: тогда весь стенд считается занятым.
- **`docker build`** выполняется в dockerd/buildkit, а не в cgroup задачи, так
  что пик задачи — несколько MiB, сколько бы ни потребляла сборка. Резервируйте
  память сборки как стенд без `--docker-project` и запускайте сборку через
  `aq submit --within RES_ID`.

### Простаивающие резервы

Выданный резерв с `--docker-project`, у которого за `[reservations] idle_after`
(10 минут; `"0s"` отключает) не работала ни одна вложенная задача и не было ни
одного запущенного контейнера его docker-проекта, получает событие
`reservation_idle` для сессии и оператора: `reservation … holds 1.5 GiB stand +
256 MiB task budget and 2 cpus, but for 10m0s no nested task ran and docker
project … had no container; aq release … if you no longer need it`. Оно
приходит один раз на каждый период простоя и снова после следующего; оно же
будит `aq wait --until expiring`. Освобождайте резерв между пакетами работы и
резервируйте заново под следующий: история сделает следующий резерв дешёвым.
Резерв без docker-проекта не отслеживается: aq не может понять, поднят ли его
стенд.

### Истечение и неудачное снятие

- За `expiry_warning` (15 мин) до конца срока резерв переходит в `EXPIRING`, и
  записывается предупреждение «продли или будет снят».
- По истечении срока резерв переходит в `TEARING_DOWN` и запускается скрипт
  снятия (одновременно не больше `teardown_concurrency`; остальные ждут слота в
  `EXPIRING`). Код 0 → `TORN_DOWN`, память возвращается в пул.
- Если в резерве ещё работают вложенные задачи, он не снимается: срок
  сдвигается до их дедлайна (`started_at + timeout + 2 × cancel_grace`),
  `aq status` показывает `ttl held: yes`, новые `--within` отклоняются.
  Как только последняя вложенная задача закончилась, резерв снимается сразу,
  не дожидаясь сдвинутого срока.
- Ненулевой код, таймаут или OOM скрипта → `TEARDOWN_FAILED`; unit снятия
  пропал без результата → `TEARDOWN_UNKNOWN`. В обоих случаях резерв
  **остаётся в учёте пула**, автоматических повторов нет. Разберитесь со
  стендом (`aq logs <id> --stream stderr` показывает логи последней попытки,
  все попытки лежат в `jobs/<id>/teardown-<n>/`) и выберите:

```sh
aq teardown --retry "$id"  # запустить скрипт снятия ещё раз
aq release --force "$id"   # стенд убран вручную: освободить без скрипта
```

Падение или перезапуск демона снятие не прерывают: unit работает сам, а новый
демон забирает его результат.

Коды `aq wait` для резерва (возвращается, как только резерв вышел из очереди):

| Код | Значение |
|---|---|
| 0 | `GRANTED`, `EXPIRING` — резерв выдан |
| 4 | `CANCELLED` |
| 5 | `REJECTED` |
| 6 | резерв больше не удерживается: `RELEASED`, `TEARING_DOWN`, `TORN_DOWN`, `TEARDOWN_FAILED`, `TEARDOWN_UNKNOWN` |

Уведомления о выдаче из очереди, истечении и превышении заявки идут владельцу;
истечение, удержание задачами, итог и принудительное снятие — оператору (см. ниже).

## Уведомления

Клиент обнаруживает сессию по процессу агента, из которого запущен aq (процесс с
именем из `stats.agent_processes`: Codex, Claude Code, OpenClaude). Сначала
берётся своя переменная идентичности — которой у агента при запуске не было или
которая отличается от полученной им (Codex `CODEX_THREAD_ID`, Claude
`CLAUDE_CODE_SESSION_ID`), — затем подтверждённый файл сессии этого процесса
(`~/.claude/sessions/<pid>.json`, `~/.openclaude/sessions/<pid>.json`); так
распознаётся OpenClaude: переменной он не экспортирует. Если среди предков нет
агента (обычный шелл, tmux, systemd unit), решают переменные настроенных
адаптеров, как раньше, и несколько непустых неоднозначны: submit/reserve
завершаются с кодом 64, MCP требует явные `client` и `session_id`.
`AQ_NO_PARENT_SESSION=1` выключает поиск по предкам. `--client NAME --session S`
задают их явно и выключают поиск; `--no-notify` у submit/reserve
отключает только уведомления сессии. Без обнаруженной сессии CLI работает как
`cli`. Указанный push-адаптер без сессии — ошибка; отсутствующая в PATH демона
команда доставки отклоняет заявку до сохранения. PATH сервиса включает
`%h/.local/bin:/usr/local/bin:/usr/bin:/bin`.

У суб-агента Codex в режиме multi-agent v2 свой `CODEX_THREAD_ID`, но Codex
не принимает `codex queue` в тред суб-агента. Если сессия (обнаруженная или
заданная через `--session`) — такой суб-агент, aq записывает вместо неё тред
выше по дереву суб-агентов: он берётся из строки `session_meta` в начале его
rollout-файла в `$CODEX_HOME/sessions` (по умолчанию `~/.codex`). Уведомления
по заявке получает родительская сессия; `aq list --mine` и `aq list --session`
из суб-агента находят его заявки под этим тредом, рядом с заявками родителя.
Суб-агент, которому итог нужен до завершения, ждёт его через `aq wait ID`. Если
rollout прочитать не удалось, id остаётся как есть.

Новый push-клиент добавляется без правки ядра:

```toml
[[agents]]
name = "pi"
identity_env = "PI_SESSION"
delivery = "push"
command = ["pi", "send", "{session}", "{text}"]
```

Если есть хотя бы один `[[agents]]`, список **заменяет** умолчания целиком.
Команда — argv без shell; также поддерживаются `{event_id}`, `{item_id}`,
`{kind}`. `delivery = "client-wait"` требует пустую command.

После submit/reserve Claude запускает `aq wait ID` с `run_in_background` и
заканчивает ход; Codex получает пинг автоматически. `aq wait RES_ID --until
expiring` ждёт предупреждения об истечении, о превышении заявки стенда или о
простое резерва. Если он вернулся с `GRANTED`/`stand_over_declared`/
`reservation_idle`, обработайте и подтвердите событие, затем запустите этот
waiter снова фоном для будущего истечения.

```sh
aq list --mine             # свои активные + завершённые с неподтверждёнными событиями
aq list --session SESSION  # явный фильтр
aq result ITEM_ID
aq ack EVENT_ID            # после записи результата в чек-пойнт
```

Событие атомарно сохраняется вместе с изменением состояния. Push/webhook
повторяются с backoff и jitter до успешной доставки (sent); sent без ack
повторно не будит сессию. Падение демона может дать дубль с тем же event_id:
сверяйте квитанцию и пропускайте уже обработанные события. Ack до захвата
события отменяет доставку, после захвата пинг ещё может прийти. Сообщение,
доставленное через минуту и больше после события, говорит об этом второй
строкой (`delayed 6m0s (delivery was retried): the event is from …; check aq
result before acting on it`). `aq wait`
показывает доставленные event IDs; прерванный waiter можно запустить снова.

Операторские тревоги включаются через конфиг:

```toml
[webhook]
url = "https://hooks.example.org/aq"
token_file = "/absolute/path/to/token"
timeout = "10s"
```

POST с `Content-Type: application/json`, `Idempotency-Key: EVENT_ID`, при токене
`Authorization: Bearer TOKEN`. Токен читается заново при каждой попытке.
Тело содержит `event_id, kind, audience, item_id, item_kind, item_name, state,
reason, project, session_id, client_type, detail, text, created_at` (RFC3339).
Значений env, скрипта снятия и логов в уведомлениях нет; текст ограничен 8 KiB.
Без URL операторские события сохраняются skipped. Через `give_up_after`
неудачная доставка становится failed; сбой session-доставки создаёт
`delivery_failed` оператору, сбой операторской — только логируется.
Пороги и таймауты — в `[notify]` примера конфига. `aq doctor` показывает
`ADAPTER_UNAVAILABLE`, `WEBHOOK_FAILING`, а также отключённый webhook.

Чтобы получать тревоги в Telegram, запустите [Gong](https://github.com/creatorofuniverses/gong)
с отдельным ботом и задайте `format = "gong"`: aq отправляет запрос Gong
`/notify` вместо своего JSON — HTML-сообщение (тип, элемент, состояние, деталь и
`aq result ID`) со значком статуса в начале (✅ готово, ❌ сбой, ⚠️ стоит
посмотреть, ⏸️ допуск закрыт, ⏳ истекает или удерживается, ❓ неизвестно,
🔄 демон перезапущен), `level` по серьёзности (`error` — неудачное снятие и
инфраструктурные сбои, `warning` — закрытый допуск, принудительное освобождение,
стенд больше заявленного и тревоги по диску, временному хранилищу, свопу и
сессиям, `info` — снятие этих тревог) и тип события в `category`. `api_token`
Gong кладётся в `token_file`.

```toml
[webhook]
url = "http://127.0.0.1:8082/notify"
token_file = "/home/USER/.config/agent-queue/gong-token"
format = "gong"
```

Демон отправляет операторские уведомления о заполнении `/tmp` и свопа,
памяти сессий агентов, простаивающих сессиях и элементах `/tmp` со статусом
`orphan` или `candidate`. Для первых четырёх тревог берётся среднее за
`[alerts].window`. Заполнение `/tmp` считается по большему из процентов
занятых байтов и inode. Эпизод начинается при достижении порога и завершается
ниже половины порога. Тревога по брошенным элементам открывается и
закрывается после двух полных проходов сканера по расписанию. Нулевое значение отключает
соответствующую тревогу. Пороги перечислены в секциях `[tmp]`, `[host]`
и `[sessions]` примера конфига.

Если проход сканера `/tmp` длится два интервала сканирования, демон один раз
пишет предупреждение об этом проходе в журнал. Интервал задаётся параметром
`tmp.scan_interval`.

## MCP

Один бинарник работает как stdio MCP-сервер; демон должен быть запущен отдельно.
Примеры подключения (выполните самостоятельно):

```sh
claude mcp add --transport stdio aq -- /home/USER/.local/bin/aq mcp
openclaude mcp add --transport stdio aq -- /home/USER/.local/bin/aq mcp
```

В конфиге Codex:

```toml
[mcp_servers.aq]
command = "/home/USER/.local/bin/aq"
args = ["mcp"]
env_vars = ["XDG_RUNTIME_DIR"]
```

Либо задайте `[mcp_servers.aq.env] AQ_RUNTIME_DIR = "/run/user/1000/agent-queue"`
(для своего UID), при нестандартных путях также AQ_STATE_DIR и AQ_CONFIG.
Codex 0.164 фильтрует окружение MCP: сессия автоматически не передаётся.
Для `queue_submit`/`queue_reserve` передавайте **client и session_id** текущей
сессии явно, либо осознанно `no_notify: true`. Неизвестная идентичность —
ошибка, а не молчаливое отключение уведомлений. Если launcher передал правильную
переменную сессии в MCP env явно, aq обнаружит её.

Инструменты: queue_submit, queue_reserve, queue_extend, queue_release,
queue_cancel, queue_status, queue_result, queue_list, queue_ack, queue_logs, queue_estimate.
`cwd` и `teardown_file` абсолютные; queue_logs: tail 1..2000 (по умолчанию 200),
без follow. MCP не будит простаивающую сессию: Claude всё ещё запускает
`aq wait ID` фоном после постановки через MCP; Codex получает daemon push.

## Хук

`aq hook pretooluse` мягко напоминает о тяжёлой команде вне aq: pytest с `-n`,
compose up/run, docker run. Он не обращается к демону, не блокирует и при ошибке
молчит. Шаблоны — `[hook].patterns`; сегменты, уже запущенные через `aq`, и
тела here-документов (текст, который команда пишет, например файл с упоминанием
`pytest -n 8`) пропускаются. В счётчик hook-hits.jsonl пишутся только
время, индекс шаблона и клиент, без текста команды; ротация после 1 MiB.

Установка не меняет настройки хуков. Вручную объедините нужный фрагмент
[Claude](../deploy/hooks/claude-settings.json) или [Codex](../deploy/hooks/codex-hooks.json)
с настройками клиента (не перезаписывайте существующие hooks). Фрагмент Claude
подходит и OpenClaude (`~/.openclaude/settings.json`, тот же формат).
В обоих фрагментах хуков matcher `Bash`; Codex требует доверить новое
определение через `/hooks`.
Скилл aq ([Claude](../deploy/skills/claude/aq/SKILL.md), [Codex](../deploy/skills/codex/aq/SKILL.md))
описывает, как агенту работать с aq: что считать тяжёлым, как оценить память,
когда `submit`, а когда `reserve` со стендом, как получить результат и убрать за собой.

## Восстановление

- Если демон упал или был перезапущен, задачи продолжают работать сами; при
  старте демон сверяет БД с systemd и забирает результаты завершившихся задач
  (их записывает `ExecStopPost` unit задачи в `jobs/<id>/result.json`).
  Задача, чей unit исчез без результата, получает `LOST`.
- `systemd` перезапускает упавший демон сам (`Restart=on-failure`).
- `aq wait` переживает перезапуск: переподключается и сообщает результат.
  Оператору приходит событие `daemon_restarted` — штатной ли была остановка.
- Пока демон восстанавливается, новые задачи не стартуют.

## Ограничения текущей версии

- Смерть сессии-владельца резерва не определяется; автоматического снятия по
  этому признаку нет.
- Оценки не гарантируют время старта; посекундные выборки CPU задач пока не собираются.
- Только Linux с systemd и cgroup v2, только пользовательский режим.

## Разработка

```sh
just build              # bin/aq
just test               # go test -race ./...
just test-integration   # go test -tags integration -p 1 ./... (реальный systemd)
just test-install       # рецепты install/uninstall во временный каталог
```

Интеграционные и e2e-тесты (`test/e2e/`) запускают настоящие units в отдельных
слайсах `aqtest.slice` и `aqe2e.slice` с пулом 1 GiB (снятия резервов — в
`aqtesttd.slice` и `aqe2etd.slice`) и после себя их останавливают;
установленный `aq.service` им не нужен.
